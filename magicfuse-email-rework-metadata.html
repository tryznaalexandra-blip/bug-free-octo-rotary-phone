Most Salesforce rework doesn’t start during deployment.
It usually starts earlier — in metadata decisions that seem operationally minor at the time.

A few examples we see repeatedly in growing Salesforce environments:

Area Common pattern Lower-maintenance approach
Access management Profiles overloaded with object access and business logic Permission Sets + Permission Set Groups organized by job function
Automation Complex Flow logic built on inconsistent data quality Validation rules, duplicate management, and matching logic before automation expands
Sandbox strategy Developer sandboxes used for integration-heavy testing Partial or Full sandboxes when async jobs, integrations, or sharing behavior matter
Integrations Sync logic documented informally across teams Shared integration inventory: systems, objects, direction, schedules, external IDs
Change tracking Schema and Flow decisions stored in tickets or tribal knowledge Lightweight decision logs tied to deployments and architecture changes

These aren’t architecture “nice-to-haves.”
They usually influence how maintainable the org becomes as the implementation evolves.

For example:

• Permission Set Groups simplify long-term access governance as teams scale.
• Sandbox fidelity becomes more important once integrations and async processing affect production behavior.
• Integration traceability reduces troubleshooting time when ownership changes across vendors or internal teams.

Salesforce complexity rarely comes from one large decision.
It usually accumulates through small operational gaps over time.
